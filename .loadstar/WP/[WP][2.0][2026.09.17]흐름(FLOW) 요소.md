### GOAL
전체 흐름을 한 장의 그림으로 보고, 필요한 단계만 하위 FLOW로 펼쳐 들어갈 수 있게 한다 — 단계 하나가 원자적 작업이거나 다른 흐름들의 합성이라는 점에서 함수형 언어의 합성 구조와 같은 모양이다.

`DIAGRAM`은 순수 mermaid로 두고(다른 뷰어에서도 그대로 그려진다), 노드와 요소의 연결은 코드블록 **밖**의 `REFERENCES`에 둔다 — 그래야 구조 추출기·검증기가 관계를 볼 수 있다.

이 WP의 이번 범위는 **0단계**: 스펙 부록 + `.loadstar/FLOW/` 인식까지. 이것만으로 기존 mermaid 렌더러가 흐름도를 그대로 그려주므로, 문법이 몸에 맞는지 실사용으로 먼저 확인한 뒤 1단계 이후를 착수한다.

### ISSUE
- mermaid가 렌더한 SVG의 노드 element id는 원본 노드 id 그대로가 아니다(`flowchart-<id>-<n>` 형태로 관측됨). 1단계 클릭 바인딩은 이 패턴에 의존하므로 실측 후 구현하고, 패턴이 바뀌어도 그림 자체는 깨지지 않도록 바인딩 실패를 무해하게 처리한다.
- 노드 id는 영숫자로 제한한다 — `REFERENCES`의 키이자 SVG 매칭 키인데, 한글 id가 SVG id로 어떻게 변환되는지 보장이 약하다. 라벨은 자유.
- 구조 추출기는 `DIAGRAM` 코드블록 **안**을 읽지 않는다 — 간선 위상(a -> b)은 색인 대상이 아니다. 색인되는 것은 `CONNECTIONS`와 (3단계 이후) `REFERENCES`뿐이다.
- FLOW가 서로를 참조하면 무한 전개가 가능하다 — 2단계 펼침에 깊이 상한, 3단계 검증기에 순환 보고가 필요하다.
- **분기에서는 화살표 목록이 주된 경로다.** 노드 섹션의 `뒤에 추가`는 갈래가 여럿이면 그 갈래를 **전부** 새 노드로 우회시키고 조건 라벨도 함께 옮긴다(확인 대화상자로 알린다). 특정 갈래 하나에만 넣으려면 화살표 목록의 `↳`를 쓴다 — 이쪽은 조건 라벨이 분기 쪽에 그대로 남는다(`ok -- 예 --> 새노드`, `새노드 --> 원래대상`).
- 펼침 판단은 **참조가 FLOW인지**만 본다 — 도형은 보지 않는다. 손으로 쓴 파일에서 사각형 노드가 FLOW를 가리키고 있어도 펼쳐진다(관대하게 동작). UI에서 연결할 때는 도형을 자동으로 맞춰주므로 새로 만드는 그림에서는 이 어긋남이 생기지 않는다.
- **하위 흐름을 새로 만드는 통로는 아직 없다.** `종류 = 하위 흐름`으로 추가하면 도형만 생기고, 실제 하위 흐름이 되려면 `+ FLOW`로 파일을 먼저 만든 뒤 연결해야 한다. 노드에서 바로 파일을 만들어 연결하는 버튼은 실사용으로 필요성을 확인한 뒤 판단하기로 보류(2026-09-17).
- 하위 흐름 펼침은 **보기 모드 전용**이다. 합성된 그림에서 자식 노드 id에는 `<노드id>__` 접두어가 붙어 부모 문서의 노드가 아니므로 선택·편집·클릭 대상이 되지 않는다 — 그림 편집 모드는 언제나 접힌(원본) 그림을 다룬다.
- 펼침은 **한 단계만** 한다. 펼쳐진 자식 안에 또 하위 흐름이 있어도 그건 접힌 채로 그려진다 — 접두어가 중첩되면 클릭 대상 매핑이 복잡해져 지금은 범위 밖으로 둔다.
- 하위 흐름의 **입구·출구가 하나로 정해져야** 펼칠 수 있다(들어오는 화살표가 없는 노드 = 입구, 나가는 화살표가 없는 노드 = 출구). 여러 개면 부모 화살표를 어디에 이을지 알 수 없어 칩 옆에 사유만 표시한다. 입구·출구가 `((시작))`/`((끝))`이면 그리지 않고 흡수한다.
- mermaid는 **문서에 붙어 있지 않은 요소를 그리지 못한다**(치수를 재기 때문, 실측: `Cannot read properties of null (reading 'getAttribute')`). 합성본을 분리된 div에 그리려다 실패했고, 임시 컨테이너를 DOM에 먼저 끼워 넣고 그린 뒤 결과만 옮기는 방식으로 고쳤다.
- 화살표 끝을 바꾸면 그 자리에 실려 있던 노드 정의가 밀려난다(`edge --> join(( ))`의 대상을 바꾸면 `join`의 도형이 사라진다) — `setEdgeEndpoint`도 정의 복원을 탄다. 아래 항목과 같은 함정이다.
- **줄을 지우거나 다시 쓰면 그 줄에 실려 있던 이웃 노드의 정의가 날아간다** — 이 파일 형식의 가장 흔한 함정이다. 두 번 겪었다: 삭제(`n --> parse[[요소 파싱]]`에서 n을 지우면 parse가 맨 사각형이 됨)와 삽입(`begin --> scan[.loadstar 스캔]`의 오른쪽을 새 노드로 바꾸면 scan의 라벨이 사라짐). 편집 전에 정의를 모아뒀다가 남은 줄에 되돌려 놓는 방식으로 고쳤다(`collectDefinitions`/`restoreDefinitions`). **줄을 지우거나 다시 쓰는 편집을 새로 추가할 때는 반드시 이 복원을 같이 걸어야 한다.**
- 화살표를 끊으면 그 연결로만 이어져 있던 노드는 그림에서 떨어져 나온다(사라지는 것처럼 보인다). 확인 대화상자로 미리 알리고, 그 노드에 걸린 참조는 "그림에 없는 참조" 경고로 드러난다 — 참조를 자동으로 지우지는 않는다.
- 조건 라벨 표기는 원문 스타일을 유지한다 — `-- 예 -->`로 쓰여 있으면 그대로, `-->|예|`면 그대로. 라벨이 없던 화살표에 라벨을 붙일 때만 `-- 예 -->` 형을 쓰고, 점선·굵은선처럼 그 표기가 안 먹는 화살표는 `|예|` 형으로 간다.
- 라벨이 비면 `s1[]`이 되어 mermaid가 파싱에 실패한다. `nodeExpr`에서 종류별 기본 라벨("새 단계" 등)로 채우고, 노드를 만든 직후 라벨 입력칸에 포커스를 줘서 바로 고쳐 쓰게 한다. 병합점만 빈 라벨이 규약이라 예외다.
- 그림 편집 되돌리기는 **저장 후에는 소용없다** — 파일에 쓴 뒤로는 git 이력이 담당한다.
- 팔레트를 6종(step/branch/merge/subflow/store/terminal)으로 시작한다. map/filter/external은 실사용 전 확정하지 않는다 — 쓰이지 않는 요소를 스펙에 남기는 것이 2.0이 1.0에서 걷어낸 유형이다.

### COMMENT
**추가 동작을 병렬/삽입으로 나눈 이유** (2026-09-17, 사용자 결정): `앞에 추가`/`뒤에 추가`는 방향을 말할 뿐 결과를 말하지 않아, 분기 노드에서 무엇이 일어나는지 예측하기 어려웠다. 병렬(갈래를 하나 더 낸다)과 삽입(기존 갈래를 밀어 사이에 끼운다)은 결과 자체를 이름으로 삼는다. `앞에 추가`는 삽입의 반대 방향일 뿐이라 없애고, 앞쪽에 넣어야 하면 앞 노드를 골라 삽입하거나 화살표 목록의 `↳`를 쓴다.

**합류를 다루는 방식** (2026-09-17, 사용자 결정): 앞서 "새 갈래 추가"에 대상 선택을 달아뒀던 방식은 합류가 *추가*의 옵션으로 묻혀 직관적이지 않았다. 대신 두 가지로 나눴다 — 이미 있는 화살표의 **끝을 바꾸는 것**(화살표 행의 드롭다운)과, 화살표를 **새로 잇는 것**(`연결`). 분리 후 병합은 "병렬 추가로 갈래를 내고, 각 갈래 끝에서 같은 지점으로 연결"이 된다.

**FLOW 삭제를 막는 이유** (2026-09-17, 사용자 결정): 다른 요소의 "삭제"는 `.del`을 덧붙여 목록에서 숨기는 되돌리기 쉬운 동작이지만, FLOW는 그림 한 장이 통째로 들어 있어 잘못 치웠을 때 잃는 것이 크다. 노드가 하나라도 있으면 막고, 비우고 지우든 탐색기에서 직접 옮기든 한 번 더 의식하게 만든다.


**`DIAGRAM`을 LOADSTAR 문법이 아니라 mermaid 원문으로 둔 이유** (2026-09-17, 사용자 결정):

- 처음엔 `STEPS`/`FLOW` 전용 문법으로 쓰고 UI가 mermaid를 생성하는 안을 제시했으나, mermaid를 원본으로 쓰는 쪽으로 정해졌다. 도형이 곧 노드 종류를 나타내므로 팔레트를 표현하는 데 mermaid 문법이 그대로 쓸모 있고, GitHub 등 다른 md 뷰어에서도 그림이 그대로 나온다.
- 이 선택의 유일한 손실(흐름이 코드블록 안에 갇혀 추출기가 못 봄)은 `REFERENCES`를 코드블록 밖 정식 섹션으로 분리해 상쇄했다. 색인·검증에 필요한 것은 "어느 노드가 어느 요소인가"이지 간선 위상이 아니다.
- 노드 종류를 파일에 따로 선언하지 않는다 — mermaid 도형이 곧 종류라는 규약(부록의 팔레트 표)으로 충분하고, 선언을 두면 도형과 선언이 어긋날 수 있다.

**파서를 프론트에 둔 이유** (2026-09-17):
